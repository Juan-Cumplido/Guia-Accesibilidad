Accessible User Stories

Requirement practice that documents accessibility needs in an agile format and maintains traceability with acceptance criteria, backlog items, and tests.

About this practice

Here you should answer three things:

What it is
An accessible user story is a story written from the user's need, explicitly incorporating an accessibility condition that can be verified.
What it is for
It helps translate accessibility requirements into an understandable format for analysis, design, development, and testing.
When to use it
Mainly in the requirements phase, during elicitation, backlog refinement, and definition of acceptance criteria.

Structure of the practice

Accessible user stories extend traditional agile user stories by explicitly incorporating accessibility requirements and verifiable acceptance criteria. This structure helps development teams understand user needs, design inclusive solutions, and validate accessibility throughout the software development life cycle.

Example

As a keyboard-only user, I want to move through the form fields in a logical order so that I can complete the registration process without using a mouse.

Acceptance criteria

  • All interactive elements can be reached using the keyboard.
  • The focus order follows the visual and logical reading sequence.
  • Errors are identified with text and are announced in a clear way.
  • The story is linked to the corresponding WCAG criteria.

Keyboard interaction

  • Tab: moves focus to the next interactive element.
  • Shift + Tab: moves focus to the previous interactive element.
  • Enter or Space: activates buttons, links, and controls when applicable.
  • Escape: closes dialogs, menus, or temporary panels when present.

WCAG Guidelines covered

  • 2.1.1 Keyboard — Level A The functionality must be operable without a mouse.
  • 2.4.3 Focus Order — Level A The tab order must follow a logical sequence.
  • 3.3.1 Error Identification — Level A Errors must be indicated in a clear and detectable way.
